# 07 — 判定方法（自包含版）

> 本文把本横评的**判定法**写成脱离任务目录也能独立阅读的版本：任何读者只拿 `critic_doc/` 这一套文档，
> 也应能复核 `01`–`06` 的每一条判定。文中不依赖任务内部的 `design.md` / `implement.md`；
> 凡引用取证细节处均指向同类交付文档（`evidence/` 分片、`02-matrix.md` 等）。
> 版本面：Pi `1.2.0`（已安装产物）、Norma `../Norma@52f17dd`、myflow `@0a702fa`。

---

## 1. 三层模型

横评不是「A 有没有 X、B 有没有 X」的二元比较，而是三层：

| 层 | 对象 | 归属 | 可改性 |
| --- | --- | --- | --- |
| L1 参照 | Norma（Go SDK，`../Norma`） | 外部参照 | 只读参考 |
| L2 Pi | Pi 运行时 **1.2.0** + 用户级扩展 | Pi | **不可改**，只能依赖或规避 |
| L3 自有 | myflow（仓库根 `.pi/` + `.myflow/`） | 用户拥有 | 可改 |

判定目标不是「myflow 有没有 X」，而是四问：
**① X 归谁？② 若归 myflow，靠什么强制？③ myflow 假设了 Pi 的哪些行为？④ myflow 有哪些 Norma 没有的能力？**

---

## 2. 归属域（Attribution Domain）——关键修正，不可省

「L2 = Pi」的二分**不够用**：L2 内部还分「Pi 内核」与「用户级第三方扩展」，
且后者会**冒充** Pi core 或 myflow 的能力。因此每个非空判定都带域码：

| 域码 | 名称 | 实体位置 | 算「Pi 内建」？ |
| --- | --- | --- | --- |
| `A-PI` | Pi core | `~/.bun/install/global/node_modules/@earendil-works/*` | ✅ 是 |
| `A-EXT` | **用户级第三方扩展** | `~/.pi/agent/npm/node_modules/`、`~/.pi/agent/extensions/`、`~/.pi/agent/skills/` | ❌ **否**（算用户环境已有） |
| `A-MF` | myflow | 仓库 `.pi/`、`.myflow/` | ❌ 否（L3） |
| `A-MCP` | 外部 MCP server | `~/.pi/agent/mcp.json` 指向的服务 | ❌ 否 |
| `A-NONE` | 无人提供 | — | — |

**`A-EXT` 分级规则（防过度乐观）**：`A-EXT` 提供的能力**一律不得**记为「Pi 内建」（`V-PI`），
只能记为 `V-EXT`。理由：用户级扩展可被卸载、可被运行时改坏，其存在不构成 myflow 的设计保证。
若某项**仅**由 `A-EXT` 提供且处于 myflow 核心流程上，须在风险登记册登记。

> **单点误判实例（本横评最贵的一处）**：工具列表里的 `Agent` / `StopAgent` / `MessageAgent` / `AgentStatus`
> **不是** Pi core，也**不是** myflow，而是 `A-EXT` 的 `pi-subagents-lite` 注册的；
> myflow 的 `myflow_subagent` 才是 `A-MF`。两者名字都像「子代理」。不做域码区分，`SUB` 域必错。

## 3. 证据规则

### 3.1 证据等级

| 代号 | 名称 | 可用性 | 例 |
| --- | --- | --- | --- |
| `E0` | 运行时自证 | ✅ 最高 | `pi --version` → `1.2.0`；`ls ~/.pi/agent/...` |
| `E1` | 安装版权威文档 | ✅ | `pi-coding-agent/docs/compaction.md:134` |
| `E2` | 安装包公开 API / 类型快照 | ✅ | `@earendil-works/*` 导出、仓库内 Pi 类型快照 |
| `E3` | myflow 源码与测试（本仓库当前提交） | ✅ | `.pi/extensions/myflow/index.ts:237` |
| `E4` | Norma 源码 / README（`../Norma` 当前提交） | ✅ | `Norma/noa/tier.go:33` |
| `E5` | `Desktop/pi` 源码（**1.0.4**，落后于运行时） | ⚠️ **仅作推断** | 必须写成「推断（依据 1.0.4 源码 …）」 |
| `E6` | 模型记忆、印象、常识 | ❌ **禁止** | — |

**硬规则**

- `E5` **不得**作为任何缺口判定的唯一依据（凡以其为据者结论必须写成推断）。
- `E1`/`E2` 的引用必须带**版本号 `1.2.0`**，否则视为无效证据。
- L1 断言引用 `E4`；L2 断言引用 `E0`/`E1`/`E2`；L3 断言引用 `E3`。

### 3.2 引用格式

```
<相对路径>:<行号>            // 代码/文档精确定位
<相对路径> §<小节标题>        // 大文件定位
<绝对路径>                   // 项目外（Pi 安装目录、~/.pi/）
```

禁止裸写「Pi 支持 X」「Norma 做了 Y」而不给路径。

### 3.3 负向断言规则（最高风险断言）

「Pi 没有 X」「myflow 没做 Y」是**最容易出错**的断言——本横评开工时就犯过一次：
先前判定「`docs/compaction.md` 未描述压缩与扩展注入的交互」，实为**检索模式过窄导致的假阴性**
（实际 `:134`、`:138` 直接命中）。因此负向断言必须写成结构化形式，且**不得单独**支撑判定：

```
(NEG) 语料=<扫描范围，须穷举文件类型与目录>
      检索式=<完整正则或关键词集合，多个用 |>
      命中=<0 或 命中文件:行>
      残余风险=<哪些表述方式可能骗过这个检索式>
```

`NEG` 还必须**再通过 §6 归属测试**，才能支撑「Pi 内建」或「真缺口」。
教训：检索「某概念是否存在」时，必须同时检索**该概念的正面枚举**与**相邻章节标题**，
不能只检索自己预期的措辞。本横评的全部 `NEG` 集中列在 `08-coverage.md` §3。

### 3.4 版本规则

- Pi 侧一律以 **1.2.0** 安装产物为准（`E0`/`E1`/`E2`）。
- 源码工作区 `Desktop/pi` 为 **1.0.4**：仅可解释「为什么 1.2.0 行为如此」，结论一律降级为推断。
- 版本敏感条目在矩阵中显式标注 `[v1.2.0]`。

### 3.5 禁止事项

- ❌ 以「我当前能用什么」推断 Pi core 能力（**认知陷阱**：从会话内部看，Pi core 与扩展/myflow 注册的工具是融合的）。
- ❌ 把 `A-EXT` 的能力算作 `A-PI` 或 `A-MF`。
- ❌ 无路径的印象式判断。
- ❌ 把推断写成事实。

## 4. 强制层级（Enforcement Ladder）

### 4.1 强度轴

| 代号 | 名称 | 判据（如何证明） | 失效方式 |
| --- | --- | --- | --- |
| `E-C` | **代码强制** | 存在会**拒绝**的代码路径：`throw` / `return {block:true}` / 非零退出 / 显式上限 | 只有改代码才失效 |
| `E-G` | **门控 / 白名单** | 可达集合被限制：agent frontmatter `tools:`、config 开关、事件 allowlist | Pi 行为或配置变化 |
| `E-P` | **提示词约定** | 仅存于 prompt / agent md / skill 文本，靠模型自律 | **模型不遵守即失效** |
| `E-N` | 无 | 无任何机制 | — |

排序：`E-C` > `E-G` > `E-P` > `E-N`。**必须标注施加强制者**：`E-G[Pi]` ≠ `E-G[myflow]`。
写 `E-C[myflow]` 时须给出代码位置与对应测试。

### 4.2 回归轴（与强度正交）

| 代号 | 含义 |
| --- | --- |
| `R-T` | 有测试锁定（测试回退即失败） |
| `R-∅` | 无回归保护 |

### 4.3 强度判定规则

- **R-STR-1**：Norma 为 `E-C` 而 myflow 为 `E-P`/`E-G` → 即使功能名相同，判**质量差**（`V-QUAL`）。
- **R-STR-2**：强度相同但 myflow `R-∅` 而 Norma 有测试 → 判**质量差（弱）**。
- **R-STR-3**：`E-P` 条目**一律不得**记为「已覆盖」。记 `V-QUAL`（若 Norma 有）或真缺口（`V-GAP`）。

## 5. 归属码与结论码

### 5.1 归属码

| 码 | 名称 | 必要条件 |
| --- | --- | --- |
| `O-1` | Pi 内建 | `A-PI` 且 `E1`/`E2` 正向命中 |
| `O-2` | Pi**刻意**外包 | `A-PI` 文档**明示**该关注点交给扩展层（须引用原文）。**无明示则不得使用本码** |
| `O-3` | Pi 部分提供 | 原语在 Pi，**语义**由 myflow 补齐 |
| `O-4` | Pi 契约依赖 | myflow 依赖 Pi 的**未文档化或易变**行为 |
| `O-5` | 双方皆无 | `A-PI` 与 `A-MF` 均无 |
| `O-6` | **用户级扩展提供** | `A-EXT` 命中，`A-PI` 未命中 |

`O-2` 的「明示」要求是防手滑设计：不能用「Pi 说它 minimal」推出「Pi 故意外包了 X」。

### 5.2 结论码

| 码 | 名称 | 条件 | 动作 |
| --- | --- | --- | --- |
| `V-GAP` | **真缺口** | Norma 有 ∧ Pi 无 ∧ myflow 无 | 写**补足标准**（`GAP-*`） |
| `V-QUAL` | **质量差** | Norma 有 ∧ Pi 无 ∧ myflow 有，但强度/回归更弱 | 写**提升标准**（`QGAP-*`） |
| `V-OWNED` | 已承担 | Norma 有 ∧ Pi 无 ∧ myflow 有，强度 ≥ Norma | 记录，无动作 |
| `V-PI` | 非缺口 | `A-PI` 内建（`O-1`/`O-2`） | 记录；**检查 myflow 是否重复造轮子** |
| `V-EXT` | 扩展已给 | 仅 `A-EXT` 提供（`O-6`） | 记录 + 检核心流程依赖 → 可能触发风险登记 |
| `V-UP` | 运行时约束 | 只能改 Pi 才能补 | 登记运行时依赖，**不列为缺口** |
| `V-NA` | 场景无关 | 有价值低 / 与定位冲突 | 记录理由，不补 |
| `V-ADV` | **相对优势** | myflow 有 ∧ Norma 无 | 标**不可回退**（`ADV-*`） |

### 5.3 契约风险码

| 码 | 名称 | 条件 |
| --- | --- | --- |
| `R-HARD` | 硬依赖 | 未文档化 / 易变 **且** 失效后果严重（静默丢状态、任务指针错乱） |
| `R-SOFT` | 软依赖 | 有文档背书，或失效后果可观测、可恢复 |
| `R-OK` | 已自愈 | myflow 已有自身补偿路径（须给代码位置） |

> 风险码与回归轴 `R-T`/`R-∅` 是两套命名（前者 `R-HARD/R-SOFT/R-OK`，后者 `R-T/R-∅`），不可混用。

## 6. 误判防呆三测

### 测 A — 卸载测试（归属域定位）

> 假想删除全部 `A-MF` 与 `A-EXT` 资产（`.pi/extensions/myflow/`、`.pi/agents/`、`.pi/prompts/`、
> `.pi/skills/`、`.myflow/`、`~/.pi/agent/npm/node_modules/`、`~/.pi/agent/extensions/`、
> `~/.pi/agent/skills/`），仅保留 Pi core 安装目录。该能力是否仍在？

- 仍在 → `A-PI`（`O-1`）。
- 不在 → 逐层加回：只在 `A-EXT` 恢复时出现 → `A-EXT`（`O-6`）；只在 `A-MF` 恢复时出现 → `A-MF`。

**测 A 的关键**：不能只做「Pi vs myflow」两分，否则 `pi-subagents-lite` 这类用户级扩展会被误记为 Pi 能力。

### 测 B — 归属方向测试（正向）

在 Pi core 安装目录 `docs/` 与各包 API 中以**能力名词 + 其同义表述**检索：

- 命中「Pi 提供」语义 → 倾向 `O-1`。
- 命中「交给扩展 / 由你构建」语义 → `O-2`。
- 无命中 → 转测 A，并以 `NEG` 记录检索式。

### 测 C — 自证 vs 推断

凡结论唯一依据来自 `Desktop/pi`（1.0.4）或任何源码工作区 → 标 `E5` **推断**，
并在矩阵中降级显示，不得进入正式缺口条目。

## 7. 优先级评分法

不引入数值打分，用**规则判定**，避免伪精确：

| 级别 | 条件（满足任一） |
| --- | --- |
| `P0` 必补 | 真缺口 ∧（状态/数据丢失风险 ∨ 已有用户可见故障 ∨ 补足仅需 myflow 侧改动且代价小） |
| `P0-R` 风险钉住 | 硬风险 `R-HARD`（与是否缺口无关，独立成列） |
| `P1` 应补 | 真缺口代价中等；或质量差且位于**核心流程**（状态注入、任务生命周期、子代理调度） |
| `P2` 可补 | 真缺口代价高；或质量差边缘；或相对优势增强类 |
| 不补 | `V-PI` / `V-EXT` / `V-UP` / `V-NA` |

「代价」三维度：**是否需新依赖**、**是否触碰 Pi 契约**（触碰则升一级代价）、**预估规模**（小/中/大）。

## 9. 这套方法的已知局限

诚实声明，供复核者判断结论的可信边界：

1. **`O-2` 的原文只在包根 `README.md`**。Pi 1.2.0 `docs/` 40 篇**无** sub-agent / plan mode 的等价表述，
   而 `README.md:19`（「skips features like sub-agents and plan mode」）是本横评判定 `O-2` 的**唯一**权威原文。
   这既是 docs 的覆盖缺口，也意味着：**只看 `docs/` 会无法判定 `O-2`**，从而把刻意外包误记为「双方皆无」（`O-5`）。
2. **`docs/` 与包根 README 存在覆盖差**。除 `O-2` 外，OpenClaw 集成、`/share` 的 HF 路径、开发流程
   （`pi-test.sh`/`CONTRIBUTING.md`）等只在 README 出现；`docs/index.md:3` 只写「extensible AI agent」，
   无 README 的「minimal / skips」语义。故本方法对「Pi 文档面」的取证必须同时扫 `docs/` 与包根 `README.md`。
3. **`E-C` 判定依赖读代码，因而对未读部分只能抽样**。凡标 `E-C` 的条目都要求指出「会拒绝的代码行」，
   但未逐行读的文件无法保证没有遗漏的强制点；负向断言因此只声明「检索未命中」，不声明「不存在」。
4. **无法验证 Pi 未来版本行为**。所有版本敏感结论均在 `1.2.0` 上成立；Pi 一旦改压缩切点规则或事件时序，
   myflow 的若干自愈补偿会**静默**失效（见 `04-risk-register.md` 的 `RISK-02`）。
5. **`noa` 域为抽样而非逐行**。它 29 个文件、11 个能力项，实际取证为「关键文件全量 + 其余抽样」；
   `llm/openai.go`、`tool/pty_*.go`、`Norma/examples/`、`Norma/cmd/` 未读（理由见 `08-coverage.md`）。
6. **`A-EXT` 的行为随其版本变化**。本横评对 `pi-subagents-lite`（1.17.0）、`pi-mcp-adapter`（5.3.0）、
   `pi-rounded-tools` 的判定锚定在本机实测版本；其未来版本变化不在本方法的保证范围内。
7. **判定维度不含性能、安全模型与代码质量的完整对标**（超出本次范围），仅在影响能力判定时提及。
