# 怎么读这本书

全书 33 页，分六部分：序 3 页，系统篇 10 页，论证篇 8 页，上线篇 6 页，诚实篇 3 页，附录 3 页。它按"防御"的结构写，不按功能清单写——功能清单是 README 该干的事。

有三条路径，取决于你愿意给它多少时间。

## 5 分钟：先看它哪里不好

**读**：[这是什么](./what-is-myflow.md) → [为什么造它](./why-built.md) → 诚实篇三页（[缺陷登记表](../honest/defects.md)、[最锋利的三处](../honest/sharpest.md)、[如果要重写](../honest/what-i-would-redo.md)）。

**你会得到**：它想解决什么问题、为此付出了什么代价，以及三个已经被代码证实的洞——一个被一整类进程绕过的守卫、一个测试在保护却没人产生的阶段块、一条被自己的代码违反的规格。

## 30 分钟：再加一次会话的时间线

**读**：5 分钟那条路径，加[一次会话的全景](../system/overview.md)、[这个项目是哪一类](../launch/positioning.md)、[只支持 Windows + Git Bash](../design/windows-only.md)、[长驻 rpc 子进程](../design/rpc-child.md)。如果你更关心"状态到底落在哪个文件上"，把第二篇论证换成[文件即状态](../design/state-on-disk.md)。

**你会得到**：8 个 hook 的触发顺序、每个 hook 能改什么、状态落在磁盘的哪些路径上；它交付成什么样、出事了沿哪个文件查；以及两个最能代表这个项目脾气的决定——删掉测不了的分支，和一个为了"能在运行中说话"而换掉整个传输层的决定。

## 深入：整本书

| 部分 | 回答什么问题 | 页数 |
| --- | --- | --- |
| 序 | 这是什么，为什么存在，怎么读 | 3 |
| 系统篇 | 实际跑起来的是什么，按什么顺序，写哪些文件 | 10 |
| 论证篇 | 每个不寻常的选择：别人怎么做、我怎么做、为什么换、代价、什么情况下改回去 | 8 |
| 上线篇 | 这玩意儿到底交付了什么、出事怎么查 | 6 |
| 诚实篇 | 已知缺陷，按"文档漂移 / 主动权衡 / 真缺"分类，每条带证据路径 | 3 |
| 附录 | 术语、文件地图、命令速查 | 3 |

三部分的写法是固定的，不即兴发挥：

- **论证篇**每页六段，顺序不变：一句话结论 → 别人怎么做 → 这个项目怎么做 → 为什么换 → 代价 → 什么情况下我会改回去。最后一段是硬要求：一个说不出"什么条件下我会放弃它"的设计选择，多半只是习惯。
- **系统篇**每页也是六段：职责 → 触发点 → 读写哪些文件 → 不变量 → 一个最小走查 → 常见误解。
- **上线篇**每页开头一句分类判断，只说三种状态：`存在` / `部分存在` / `不存在`。写「差不多有」的格子一定是错的，而每个「不存在」都要带原因和触发条件。
- **诚实篇**按证据组织。`文档漂移` 是文档和代码已经不一致；`主动权衡` 是知道代价仍然这么选；`真缺` 是确实没做。

如果你只想读 8 页就下判断，读论证篇：那是这本书真正的论据，其余五部分是它的上下文。

## 本书的证据规则

这本书的正文是中文，但命令名、工具名、字段名、文件路径一律保持英文原样，方便你直接拿去 grep 这个仓库。

**不写行号。** 引用一律是路径加符号名，例如 `transport.ts` 的 `isFailedResult`、`turn-cache.ts` 的 `resolveActiveTaskStatus`。行号会在下一次重构后指向一段无关的代码，符号名会活下来。写作时用到的行锚只留在任务的调研笔记里，不上正文。

**只用能核对的数字。** 全书出现的计数都限于这些：8 个 Pi hook、7 个注册工具、2 个斜杠命令、`task.py` 12 个子命令、`worktree.py` 7 个、`channel.py` 10 个、4 个 workflow-state 块、8 个 skill、3 个 prompt 模板、3 个子代理定义、2 个通道 peer、38 个测试文件、版本 `0.3.0`。没有总行数，没有测试用例数——这两样在当前树里查不到，所以它们不在书里。

**只写代码支持得住的话。** 这里的守卫是一条路径边界而不是权限系统，平台只有一条代码路径，运行时要 Node 内置模块、Pi、`python3`、Git Bash、`git` 和 `taskkill`——所以这本书不会用更强的词去描述它们。反过来，它也不假装这些是免费的：每一处都在论证篇的"代价"段落里标价。

**没确认的写成待确认。** 代码读得清的就当代码事实写（例如 `subagent.ts` 里传给子进程的 `ctx.cwd` 与 `findProjectRoot` 的关系，读一遍就能定论，所以它是一条缺陷）；代码读不出、又不值得为它跑一次实验的，就标成开放问题。一个未经实测的指控和一个未经实测的吹捧一样糟。

最后一句：附录里的[命令速查](../appendix/commands.md)和[文件地图](../appendix/file-map.md)让你读完某一章后能立刻去跑、去看。这本书的每个论断都指向可以打开的文件。
