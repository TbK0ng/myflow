# 灰度与回滚：可重建，不可回滚

**分类判断：** 灰度（维度 5）**不存在**，这个形态里也没有它的位置——没有第二个用户可以被「先放一小部分」；回滚（维度 6）**部分存在**：能从 tag 造出一份内容等价的载荷，取不回当初那份字节。

## 一句话结论

这两个维度共享一个前提：**有一群不知道你在改什么的人**。灰度把风险分摊给他们，回滚在他们抱怨之前把版本退回去。这里这群人不存在——用户是作者。于是灰度是零，回滚退化成**可重建**：这个词不含「取回」，也不含「切换」。

## 维度 5 · 灰度：不存在

没有 staging 与 prod 之分，没有按百分比放量，没有 feature flag。唯一通道是 copy-in-place。

最接近的事只有一处：`--verify` 在临时目录里解压产物跑六项冒烟，跑完删掉。它是「先在别处跑一遍」，但验的是「能加载、能注册、脚本能起」，不是「新版本在真实任务上表现如何」。

**为什么没有位置。** 灰度的价值是「把风险限制在少数人身上，同时观察他们」。两个前提都不成立：没有少数人可选，也没有观察通道（没有远端遥测，见[埋点就是运行留痕](./observability.md)）。

**触发条件。** 出现第二个真实用户，或载荷以「拿不到源码 diff」的形式发出去。那时灰度的最小形态也不是百分比，而是两个版本能并存，一份能判断要不要升的 CHANGELOG 分级。代价随之而来：并存要求安装处记版本——正是下面清单的第一个空洞。

## 维度 6 · 回滚：可重建，不可回滚

三个「没有」决定了这个词只能用到哪：

1. **没有产物留存。** `dist/` 被 gitignore，产物从不进版本库；`build()` 对同名暂存目录先 `rmtree`，也没有清理策略。现在 `dist/` 里只有 `myflow-0.3.0/` 与它的 zip——**这是本机状态**：换台机器 clone 下来是空的，tag 还在。`0.2.0` 的载荷目录早就不在树上，不是被删了，是从来没被保住。
2. **安装处没有版本标记。** 载荷里没有 version 文件，`INSTALL.md` 明确要求不要把 `RELEASE.md` 复制进目标项目。于是「装的是哪一版」在磁盘上没有答案。
3. **没有 epoch 记录。** 构建时间戳只写在产物内部的 `RELEASE.md`（`built_at`）；产物丢了，字节一致的重建就没基准。

同类的还有第三方 skill：`.pi/settings.json` 把它们写成 `git:github.com/...`，不带 commit 或 tag，`.pi/git/` 整个被忽略。

### 一个能照着做的「回滚」

它实际上是**重建 + 重新部署**：

1. **确认回到哪一版。** `git tag -l` 是唯一路标（`v0.1.0` / `v0.2.0` / `v0.3.0`）。tag 不存在就没有这个流程。
2. **重建载荷。** 在那个 tag 的树上跑 `python tools/release.py --out dist --verify`。口径注意：重建只是**内容等价**，字节不一定相同（`epoch` 与 deflate 都不保证）。
3. **覆盖。** 按 `INSTALL.md` §1 逐项拷：`.pi/` 整个，`.myflow/` 下的 `agents`、`scripts`、`spec`、`workflow.md`。**`worktree.yaml` 保持项目自己那份**——它是项目配置，不是你回滚的对象。
4. **不碰这三样。** `.myflow/.runtime/`、`.myflow/tasks/` 与 `.myflow/archive/`。它们是项目状态，不随包走。代价是旧 harness 会看到新 harness 留下的条目与游标。
5. **重启。** 重启 Pi 或 `/reload`，然后 `/myflow-status`：应打印 `myflow: no_task` 或当前任务，`Task:` 与 `Approval:` 两行不空。

**残渣要自己处理。** 覆盖是逐文件拷贝，没有清单比对，「新版本有、旧版本没有」的文件会留在树里。`RELEASE.md` 的「Files by path」表按目录分组计数，不是逐文件清单；`--check` 也只说会拷多少文件。要清干净只能自己 `ls -R` 两棵树。

### 明确不可恢复的清单

| 想恢复什么 | 能不能 | 为什么 |
| --- | --- | --- |
| 某个已发布版本的载荷字节 | 只能重建，不能取回 | `dist/` 被 gitignore，`build()` 会 rmtree 暂存目录 |
| 那次构建的 `SOURCE_DATE_EPOCH` | 不能 | 只写在产物内部的 `RELEASE.md`，产物丢了没参照 |
| 某个项目装的是哪一版 myflow | 不能 | 载荷不带版本标记，`RELEASE.md` 不复制 |
| 一次历史运行的日志 | 部分 | 有保留窗口，已清理的不在（见[运行注册表](../system/runs-and-steering.md)） |
| 一次 verify 门拦过几次 | 不能 | 计数器只在会话内存里，不落盘 |
| 第三方 skill 的历史版本 | 不能 | 没有 pin，checkout 目录被忽略 |

贵的是第三行，不是前两行：前两行只影响「能不能证明我回到了过去」，第三行影响「我能不能判断该不该回去」。

## 什么情况下我会改回去

1. **出现第二个真实用户，或要在别人机器上排障。** 那时第一件要补的不是回滚流程，而是**安装处的版本标记**——几百字节，让「你装的是 0.2.0」变成可读事实。现在没做，只因唯一用户刚装完，知道自己装的是什么。
2. **发布产物需要被长期引用。** 那该把它挂到不可变的地方（release asset 而不是 `dist/`），而不是逼人重建。
3. **`dist/` 里真有两份以上载荷而没人知道对应哪次发布。** 那说明「不留存」已从选择变成噪音，该给它一条命名与清理契约。

在那之前，诚实说法是：**它没有回滚，只有「重新构建并重新安装上一版」**。这两件事差得很远，写清楚比补一层像回滚的机制有用。
