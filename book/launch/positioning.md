# 这个项目是哪一类

**分类判断：** 这是**单机、单用户、单平台的开发者工具**——交付单元是一个目录加一个 zip，安装动作是一次 `cp -r`，唯一的用户是作者本人。9 个上线维度里，3 个真的存在（构建打包、发布、版本管理），3 个只存在一半（回滚、日志与指标、可观测性），3 个在这个形态里没有位置（更新、灰度、鉴权）。

## 一句话结论

上线不是项目规模的问题，是**形态**的问题。同一张维度表，套在多人的企业项目上是工程清单，套在这里一半的格子是在问「你为什么没有飞机跑道」。所以这一篇先定形态，再让每个维度自己回答「存在 / 存在但很小 / 不存在」，并且每个「不存在」都带一个触发条件——**「没做」和「不知道要做」不是一回事**。

## 判断依据

五条，都能在树里查到。

**一、载荷是整树，不是包。** `tools/release-payload.json` 只有 `dirs: [".pi", ".myflow"]`，`trees` 与 `files` 为空；没有包名、入口、导出面、版本化 API。

**二、装法是复制，不是安装。** `tools/INSTALL.md` §1 是 `cp -r`：`.pi/` 整个，加 `.myflow/` 下的 `agents`、`scripts`、`spec`、`workflow.md`，模板复制成 `worktree.yaml`；外加钉一次 `shellPath`、接受一次项目信任。

**三、没有用户体系。** 载荷里没有登录、没有 token 校验、没有额度。三处「门」都不是鉴权：Pi 的项目信任、计划批准门（`task.py` 的 `_approval_report`，脚本自己声明它不是安全边界）、`channel.py` 的 `read_worker_guard`。

**四、CI 只有一个 runner，且不出包。** `ci.yml` 只跑 `npm run check`；唯一自动发布的产物是这本书（书不在载荷里）；出包是人在本地跑。

**五、没有远端。** 跨会话、跨进程的真相都是 `.myflow/.runtime/` 下的文件（见[文件即状态](../design/state-on-disk.md)）。这也是「遥测」与「跨进程 trace」缺得那么彻底的原因——不是没接，是没有那个位置。

## 三种现成的上线模板，一个都不套用

现成的上线方案基本有三种形态：企业级多人、团队内部服务、单机单店。一个一个说为什么用不上。

**A · 企业级多人：最不接近。** 它假设发布是一次对别人做的动作，所以有发布列车、变更审批、灰度批次、on-call；这里发布是对自己做的。能用的只有那 9 个维度的**清单本身**——我拿它当检查表，它逼我承认「更新」和「回滚」是真的没有。

**B · 团队内部服务：最接近，差一个人。** 一旦有第二个使用者，「我改过载荷」和「你要覆盖我的改动」立刻冲突——而 `INSTALL.md` 两头都要：载荷 meant to be edit-in-place，装法却是整树复制。这条登记在[灰度与回滚](./rollback.md)的不可恢复清单里。用不上 staging 与 prod：staging 的全部价值是「让少数人先踩」，而少数人只有一个。

**C · 单机单店：形态最像，假设最不像。** 单机、单实例、单用户都对，但单店软件的用户不是作者，所以它必须假设「用户不会看日志」，并为此建远程支持与备份恢复。这里用户就是写日志的人，排障链路因此建在仓库里（[三条真实事故的排障走查](./operating-the-tree.md)）。能借的是备份/恢复的心智，借来要改一个词：**可重建**，不是可恢复。

## 9 个维度，原文照抄

这张表是这一篇的地基，后五页各自展开其中几格，不再重新论证分类。

| # | 维度 | myflow 里的状态 | 一句话原因 |
| --- | --- | --- | --- |
| 1 | 构建与打包 | 存在 | `release.py` 产出目录 + 可复现 zip |
| 2 | 发布 | 存在，规模极小 | GitHub repo + `INSTALL.md` copy-in-place |
| 3 | 更新方式 | 不存在（整包替换） | 单用户单机，没有需要通知的人 |
| 4 | 版本管理 | 存在 | 三个 annotated tag，`package.json` 单一来源 |
| 5 | 灰度 | 不存在 | 唯一用户就是作者，灰度等于自己先跑一周 |
| 6 | 回滚 | 部分存在：可重建，不可回滚 | 产物不留存、安装处不记版本 |
| 7 | 日志与指标 | 部分存在 | 运行留痕齐全；成本与质量拦截没落盘 |
| 8 | 鉴权 | 不存在，且不在这个项目里 | 没有用户体系；有门，但那不是鉴权 |
| 9 | 可观测性 | 部分存在 | 有 5 类 id，没有 exception id、没有跨进程 trace |

三态词汇是刻意的：写成「差不多有」的格子一定是错的。

## 总纲

**规模决定深度，不决定 correctness。** 一条能把 0.3.0 打包成可复现 zip 的脚本，在这里必须正确；一条灰度发布流程，在这里必须不存在。把两者当成同一份清单的相邻两行，量出来的只有差距，没有信息。

后五页是一次展开：[构建、发布、更新、版本](./delivery.md) 答 1/2/3/4，[灰度与回滚](./rollback.md) 答 5/6，[埋点就是运行留痕](./observability.md) 答 7/9，[三条真实事故的排障走查](./operating-the-tree.md) 是「排查话术」的真实版，[如果它是一个产品](./if-it-were-a-product.md) 是设计预案。

## 这个判断会错在哪

分类判断最容易退化成一纸免责声明，所以它的检验标准是**哪条事实变了它就不成立**：

1. **出现第二个真实用户**——会克隆、会跑、会报问题的那种人。那时「覆盖式更新」与「安装处无版本标记」立刻从可接受变成事故来源，维度 3 与 6 必须重写。
2. **载荷以包的形式发出去**——任何让人拿不到源码 diff 的通道。那时「可重建」不再是及格线，因为用户重建不了。
3. **出现一个必须长期运行、要在 Pi 挂掉之后继续对外服务的组件**——那时「没有守护进程」这条前提消失，跨进程 trace 从「不需要」变成「必须」。

三条都没发生。在那之前，这一页的价值是把「没做」写成一格明确的判断，而不是一片看起来像遗漏的空白。
