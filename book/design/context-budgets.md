# 字节预算，而不是塞满 prompt

## 一句话结论

子代理看到的规格上下文不是一段「尽量塞」的字符串，而是一份**顺序固定、每层有字节上限、超了就留一条 omission 通知**的物化结果。买到的不是更聪明的检索，而是「同一个任务派发两次，拿到同一段上下文」。

## 别人怎么做

**整段塞进 prompt 或 `AGENTS.md`。** 把所有相关文档拼成一段，交给 Pi 的压缩机制处理。买到的是零工程。代价是它每轮都在付费，而且随任务增长而无界。

**RAG / 向量检索。** 建索引，按当前问题召回 top-k。买到的是上下文跟着问题走。代价有三层：结果不确定、不可解释（为什么是这一块）、不可复现。

**让人手挑文件。** 规划者把路径写进一个清单，注入时只读这些。买到精确和可审计；代价是清单会腐坏——文件被删、被改名，清单还在。

这个项目选第三条，并把它机械化：清单就是磁盘上的文件（`implement.jsonl` / `check.jsonl`），谁在什么时候加了哪一行都有记录。

## 这个项目怎么做

唯一的生产者是 `context-injection.ts` 的 `buildTaskContext`，顺序写死：

| # | 内容 | 单份上限 | 谁拿得到 |
| --- | --- | --- | --- |
| 1 | `prd.md` | `max_artifact_bytes` = 65536 | 所有进程 |
| 2 | `design.md` | 同上 | 所有进程 |
| 3 | `implement.md` | 同上 | 所有进程 |
| 4 | `info.md` | 同上 | 所有进程 |
| 5 | `implement.jsonl` 引用的文件 | `max_file_bytes` = 32768 | 只有 `myflow-implement` |
| 6 | `check.jsonl` 引用的文件 | 同上 | 只有 `myflow-check` |

这三个数来自 `DEFAULT_CONTEXT_INJECTION_LIMITS`，就是生效值。

预算由 `ContextBudget` 记总账（`max_total_bytes` = 131072）。每份内容入账走 `emitCandidate(完整块, 省略通知)`：完整块塞不下就退到通知，通知也塞不下就发一次终局说明并**关掉预算**。

降级是文本化的，三种标记：`[myflow: omitted <path> (<n> bytes) — <reason>]`、`[myflow: truncated at <N> bytes — read <path> for the full content]`，以及只发一次的 `[myflow: context limit reached; omitted entries remain authoritative on disk …]`。三条都在说同一件事：**被丢掉的字节还在磁盘上，你必须自己去读**；这也是模型唯一能看到的缺失信号。

读取有信任边界：清单里写一个项目外的路径，只有在 `realpath` 之后落在项目根、或落在 `channel.trusted_context_dirs` 声明的目录里才会被读；`.myflow/tasks` 本身是符号链接时，它的真实目标被自动信任。清单文件读取上限 1 MiB。不存在的 artifact 静默跳过；被两个清单同时引用的文件按 `realpath` 去重。

## 为什么换成这个

**这是本书论点在机制层的内测：如果连模型看到什么都无法复现，它产出的证据也无法复现。**

**一、可复现是硬要求，检索天生不满足。** 我需要能说「派发时它读到的就是这些字节」，RAG 只能让我说「它大概召回了这些」——对一个以证据链为卖点的项目，一句「大概」是致命的。

**二、预算让成本可见，而不是让成本消失。** 131072 看一眼就懂。它不是为省钱——128 KiB 的注入块在今天很便宜——而是为了让「上下文不够」变成一个**有名字的事件**。

**三、清单把「该读什么」变成规划阶段的产物。** `create` 把两个清单播种成空文件，`start` 拒绝「播种了但零条」的任务：没有这道门，子代理会带着**零条规格上下文**开始干活，而且它自己不知道。

一项容易误解的事：这个项目**没有**声称注入顺序等于重要性顺序，只声称顺序固定。

## 代价

**一、优先级是反的，而且是已知、故意不修的。** artifact 先于清单文件入账，所以预算紧张时先被丢掉的恰恰是规划者精心 curate 的规格上下文，而不是模型自己也能读的 `prd.md`。`.myflow/spec/harness/index.md` 把这条登记为 ordering caveat 并写明 *deliberately not changed here*。这是我不认为它能被长期容忍的理由：资源分配把「人挑过的东西」排在「机器生成的文档」之后。

**二、推到极限时连通知都会消失。** 按上限做算术：`prd.md` 与 `design.md` 各顶到 65536 就用完了 131072，此后第一个清单文件既塞不进内容也塞不进省略通知，`emitTerminalSummary` 同样拿不到空间——注入块的结尾是**干净的**。**这是按上限做的推导，不是实测**（真实注入块每份内容还带表头，落点很少正好等于上限），但它说明那三条通知本身也吃预算。

**三、五份小文件要人肉维护。** `prd.md`、可选的 `design.md` / `implement.md`、两个清单。

**四、字节不等于 token。** 预算上限和模型窗口之间没有换算代码，131072 只能当量级用。

**五、配置读取是手写正则。** `readContextInjectionLimits` 逐行正则扫 `config.yaml`；嵌套 map、锚点、列表都会被静默忽略。这一条与[拒绝优于降级](./refuse-not-degrade.md)直接冲突：那里判不了就拒绝，这里判不了就**默默地**用了默认值。

## 什么情况下我会改回去

1. **出现一个能在注入前估算 token 的工具**，并且我信得过它。那时预算该按 token 记。
2. **有一次真实的误判能归因到注入顺序**：复盘指出「`implement.jsonl` 里那份规格被预算挤掉了」。调换两段代码的顺序几乎不要钱；现在不改的唯一理由是它还没害到人。
3. **清单的 curate 成本被证明高于收益**——比如绝大多数任务最后都是 `--allow-empty-context` 启动。那时该承认这道门只对多子代理的任务有意义，把它收窄过去。

在那之前，宁可让模型读到一份有上限、带省略通知的上下文，也不给它一个随问题漂移的检索结果。
