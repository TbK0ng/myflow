# writesUnder 是边界，不是锁

## 一句话结论

`writesUnder` 回答的问题是「两路写入撞在同一棵目录树上，最坏情况有多坏」，不是「怎么挡住一个坏代理」。它把最坏情况从整棵工作树缩到一个目录，代价是它只认 `write` 和 `edit` 两个工具名——而 `bash` 按设计就是绕过它的那扇门。它既不是沙箱，也不是锁。

## 别人怎么做

五种主流做法，各自买到不同的东西：

**文件锁 / 串行队列。** 所有写入者排队。买到互斥：不需要知道谁写哪里。代价是并行度归零，一个慢写入者挡住整棵树。

**每个写入者一棵 git worktree。** 买到真正的工作树分离，合并交给 git。代价是一个代理看不见另一个的中间状态，冲突被推迟到 merge。

**容器或 OS 级原语**（job object、AppContainer、seccomp 一类）。买到「代理能不能看见这个文件」由内核回答，不靠代理合作。代价是它需要平台原语，还要在没有第二个用户的机器上做对。

**逐次权限提示。** 每次写操作问人一次。买到人的判断。代价是人必须在线，而一个跑一刻钟的 run 会问很多次。

**不约束**，只在 prompt 里写「一次一个写者」。买到零代码。代价是它只是请求，不是机制。

前四条都在回答「怎么让写入不互相破坏」，只有第三条顺带回答「怎么阻止恶意代理」。这两个问题在我的场景里权重完全不同。

## 这个项目怎么做

声明在 agent 定义里：`.pi/agents/<agent>.md` 的 frontmatter 可以写 `writesUnder: <task 内相对目录>`。三个判据，分在两个文件：

| 名字 | 在哪 | 判什么 |
| --- | --- | --- |
| `isSafeWriteScope` | `agents.ts` | 空、绝对路径、盘符、任何 `..` 段 → 不安全 |
| `declaresWriteScope` | `subagent.ts` | 只看**非空**。非空就把值注入成 `MYFLOW_WRITES_UNDER` |
| `hasWriteScope` | `subagent.ts` | 声明了**并且**安全。只有 `mode: "parallel"` 的门用它 |

前两个故意不同。如果 `declaresWriteScope` 也要求安全，一次不安全的声明就会退化成「没有声明」——子代理随即拿到整棵树的写入权。现在它拿到一个不可能通过的值，写入在子进程里 fail closed。

执行点是 `index.ts` 的 `evaluateWriteScope`，从 `tool_call` 钩子进入；四种情况全部 block：没声明、声明不安全、`path` 缺失或不是字符串、解析不出活动任务。

判定是词法的，不是 `realpath`：`normalizeWriterPath` = `resolve` 折叠 `..` 与分隔符 → 全换成 `/` → `toLowerCase`；`isWithinWriteScope` 比较 `=== root` 或 `startsWith(root + "/")`。那个斜杠是必须的，否则 `researchX` 会匹配上 `research`；小写折叠也不是可选项——NTFS 不区分大小写。同一组谓词被 `background/` 复用去校验 `myflow_bg_start` 的 `cwd`——一处规则，两个功能。

## 为什么换成这个

我拒绝锁，不是因为锁不好，而是因为在这个环境里做一个**真的**锁不便宜，而一个总能被 `bash` 绕过的锁只会制造虚假的安全感。

`myflow-implement` 与 `myflow-check` 的工具清单里都有 `bash`，这是不可选的：验证要跑测试。于是任何只拦 `write` / `edit` 的机制，对 `echo >> file` 无效。在这个前提下：

1. **锁的粒度选错了问题。** 代码无法判断两个并行 prompt 会写哪些文件——prompt 是自然语言。所以锁只能做到「全部串行」，那是用并行度换一个不存在的证明。
2. **worktree 用在错误的地方。** 子代理必须看见检查代理将要验证的那棵树。worktree 会把「代理 B 修正了代理 A 的文件」变成一次 merge 冲突。真正需要分离的场景——两个**独立任务**并行——已经由 `worktree.py` 的 7 个子命令提供，那里的分离是 git 的能力，不是 `myflow_subagent` 要重新实现的。
3. **边界对应的是可回收的损失。** 「写坏整棵树」与「写坏一个目录」在 git 下就是 `git checkout -- .` 与 `git checkout -- <dir>` 的差别：用真锁去消灭一个能回滚的损失不划算。
4. **声明是可审计的。** 并行许可取决于一个写在 agent 定义里、进版本控制、能被 diff 的字段。声明可能撒谎，但一次撒谎留在 diff 里。

所以这条机制的准确定位是：把「代理越界写」从一个静默事件变成一个响亮的 block，并把并行限制在唯一一个声明了目录的 agent 上（`myflow-research → research/`）。

## 代价

**一、它不是沙箱。** `bash` 能写任何地方，代码里写着这是设计。

**二、词法检查，不解析真实路径。** scope 里的一个符号链接可以指向外面，判定只看字符串前缀。

**三、两个近义谓词是活的陷阱。** 它们名字像、语义像，用错后果不对称：`hasWriteScope` 被误用到注入路径上，一份不安全声明就变成无边界写入。它被登记为 gotcha 而不是合并成一个函数，因为两处语义确实不同。

**四、并行基本不可用，而且许可是声明的不是观测的。** 默认 agent 没有 scope，最常见路径是串行派发；代码也不知道两个 `research` prompt 会不会写同一个文件。

## 什么情况下我会改回去

1. **出现第二个能往这棵树里派发的人。** 判据不是「有人在用」，而是「有一个人我不完全信任」；那时要的是真正的工作树分离或 OS 级原语。
2. **需要多个写者真并行改同一棵树。** 那时锁是唯一正确答案，而锁意味着边界从「拦工具」变成「换根」：每个写入者有自己的目录。
3. **`bash` 不再是子代理的必需工具**（比如出现一个能表达完整改动的结构化 patch 工具）。那时边界覆盖了全部写入面，「词法检查够用」这个前提才真正成立。
