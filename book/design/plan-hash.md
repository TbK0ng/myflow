# 用哈希锁住计划

## 一句话结论

「用户同意了」这句话本身没有内容。这个项目把它变成一件能被重算的事：`approval.json` 绑定 `prd.md` + `design.md` + `implement.md` 的字节摘要，改一个错别字批准就作废。它挡的是**忘记问**，不是**故意骗**——手写一个 `approval.json` 就能过，这一句代码里写着。

## 别人怎么做

**信任代理的自述。** 模型说「用户已经批准了这个方案」，流程继续。买到零摩擦。代价是这句话不可核对——它可能来自上一轮、来自另一个任务，或者干脆是模型为了让流程往前走而说的。

**一次性弹窗，结果管整个会话。** 用户点一次「同意」，之后与计划相关的门全部放行。买到的是「只问一次」。代价是这个同意没有宾语：同意的是当时那一版，而没人记得那一版长什么样。

**带作用域和有效期的授权令牌**（OAuth 式）。买到真正可验证的同意：签发方签名，消费方做密码学校验。代价是要有签发方、密钥和验证链，单机工具给不了。

三条路的差别在**验证发生在谁手里**：第一条没人验证，第二条验证一个布尔值，第三条验证密码学。这个项目在第二和第三之间——它验证摘要，不验证签名。

## 这个项目怎么做

三个写入点，一个读入口，一个执行点。

**哈希只有一份实现**，在 `task.py` 的 `_plan_digest`：按固定的 `PLAN_FILES` 顺序（`prd.md`、`design.md`、`implement.md`，只取存在的），每份喂进 `sha256` 的是 `文件名` + NUL + 原始字节 + NUL。文件名与 NUL 分隔让摘要在重排和拼接下不会撞车；`_plan_hash` 在某个存在的文件读不出来时返回 `None`，整条链因此 fail closed。

**写入侧两个**：`myflow_request_approval`（TUI 确认框）与 `task.py approve`（人在终端里跑）。两者都先过同一组前置检查——必须有活动任务、任务在 `.myflow/tasks/` 下、有计划文件、至少有一条已回答的选择题——才允许写文件。

**读取侧一个**：`task.py` 的 `gate-info`。`approval.ts` 与 `status.ts` 从不自己算摘要、也不自己数问题行，两者都 `spawnSync("python3", …)` 然后原样透传。`status.ts` 的注释把理由写清了：这个模块**不许**把批准状态收敛成自己的谓词，否则 `task.py` 新增一种状态时这里会悄悄少报一种。

**执行点是 `task.py start`**，顺序固定，任何一道不满足就退出 1 并只报告自己那一条：清单门 → 批准门（`_approval_report` 给出 `approved` / `stale` / `missing` / `invalid` / `unhashable`，只有第一种放行）→ 回算已答问题数。最后一步用与写入侧**同一个函数**再数一遍 `questions.jsonl`：真正放行的那一侧不能依赖写入侧诚实。

## 为什么换成这个

**一、同意必须有宾语。** 第二种做法无法回答「你同意的是哪一版」。绑定字节之后它有唯一答案，而且能被任何人在任何时间重算，不需要信任任何一方。

**二、编辑即撤回，这条规则不需要信任代理。** `stale` 不是因为某个组件判断「这次改动大不大」，而是摘要不相等。它把裁量权从代理手里拿走，交给一次相等判断——一个代理没法说服哈希。

**三、权威放在执行的地方。** 谁执行门，谁实现哈希；强制执行的那一步在 `task.py start`，所以哈希也在 `task.py`。反过来的设计（TS 算一次给 UI 看，Python 再算一次给门看）的失败形态被 spec 写下来了：*一边显示 `approved`，`start` 却拒绝，而报错不指出根因*——这是最难 debug 的一类不一致。

## 代价

**一、可伪造，而且这一点在代码里有实测。** `task.py` 的注释原文：这是一条 *convention reinforcement against forgetting*，不是安全边界；任何能跑 `bash` 的代理都能手写 `approval.json` 或传 `--allow-unapproved`。更具体地：`cmd_approve` 的 `sys.stdin.isatty()` 在此不起作用——Pi 的 bash 工具分配 pty，实测返回 `True`；Windows 上把 stdin 重定向到 `< /dev/null` 会映射成 `NUL`，同样报 `True`，只有**管道**才算非 tty。`approved_by` 因此不可信；标题里的「锁」是比喻。

**二、「改一个字就失效」会训练出反射性同意。** 让批准对错别字敏感是正确的；但门因此在正常编辑中反复触发，而一个反复触发的确认框训练出的行为，正是这道门最初想消灭的那一个：不读就点同意。机制在保护一个它同时在削弱的东西。

**三、批准路径上多了一个 `python3` 进程。** TypeScript 扩展因此有了运行期的 Python 依赖：在 `PATH` 上、同步调用、上限 5 秒（`GATE_TIMEOUT_MS`）。`myflow_request_approval` 和每一次 `/myflow-status` 刷新都付这个延迟。

**四、两种语言之间没有类型保证。** `approval.json` 的字段名、`gate-info` 的 JSON 形状、`via` 的取值，全是手维护的字符串契约；TS 侧用 `as Record<string, unknown>` 加 `typeof` 检查读它——字段名写错不会被编译器发现，只会让门返回 `missing`。

## 什么情况下我会改回去

1. **Pi 提供结构化的「用户同意」事件，并把被同意的内容摘要一起带回来。** 那时摘要的权威交给 Pi，`task.py` 只做比对。现在不做，是因为 Pi 的确认对话框只回一个布尔值：摘要必须自己算。
2. **多用户，或者代理的输入不完全由我控制。** 那时需要签名令牌而不是哈希。哈希只能证明「两次读到的字节相同」，挡不住能写文件的人；这是能力边界，不是实现缺陷。
3. **有人因为反复同意而漏看了一次真改动。** 那时我会把绑定范围收窄：只绑 `design.md` / `implement.md`，或者绑到「哪几个文件被展示过」而不是字节。
