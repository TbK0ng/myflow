# 拒绝优于降级

## 一句话结论

在一个同时住着人和代理的系统里，**沉默的降级是唯一无法被审计的失败模式**：它不报错、不留痕、无法归因。所以这个项目在运行时、文档、决策三处都选了「判不了就停下，并说清缺什么」，代价是环境不对时它什么都不做。而在 prompt 那一层这条原则**不成立**——提示词没有错误通道。

## 别人怎么做

降级是体贴的默认：没有配置文件就用内置默认值；判不出平台就选最像的那一个；shell 找不到就退到 `cmd.exe` 或 `sh`；拿不到批准就先干，反正「用户大概没意见」。

它买到的是**不卡住**：降级过的程序几乎总能让用户往前走一步，而拒绝过的程序会让用户去读文档。代价藏在事后：等到结果错的时候，你面对的是一个**正确执行了错误决策**的系统，而没有一行日志说「我换了一个 shell」。

## 这个项目怎么做

四层，前三层拒绝，第四层拒绝不了。

**一、运行时：判不了就停下。**

| 判不了的事 | 行为 | 在哪 |
| --- | --- | --- |
| 有没有可用的 POSIX shell | 拒绝，不跑命令 | `bg_runner.mjs` 的 `shellRejectionReason` |
| 解析出来的是不是 `cmd.exe` | 拒绝，**不回退**到别的 shell | 同上 |
| 计划文件读不出来 | `unhashable`，门不放行 | `task.py` 的 `_plan_hash` |
| 声明的 `writesUnder` 是否安全、活动任务是哪个 | 任一判不出就 block 写入 | `index.ts` 的 `evaluateWriteScope` |
| 有没有交互式 UI | `via: "no-ui"` 加一条指令，**绝不**编默认答案 | `ask.ts` 的 `noUiInstruction` |

`cmd.exe` 那条最能说明问题：不是懒得写，而是**写出来会错得很具体**——Node 重新加引号时把内层引号转义成 `\"`，`cmd.exe` 不接受，任何带引号的命令都会失败。一个会静默失败的 fallback 比一句拒绝更坏。同样的姿态在 `resolveShellPath` 上：它没有 `platform` 参数，也不把 WSL 的 `bash.exe` 当退路——「有效一半」只会让人先相信它。

**二、文档：拒绝让声明沉默地腐烂。** `myflow-meta` 的规则是「Prefer a test over a note」：`workflow-invariant.test.ts` 要求每个 `[required · once]` 步骤在对应 phase 块里有执行语句，`scaffold.test.ts` 要求 hook 表等于注册的 8 个。文档与代码不一致就是静默降级：读者相信它，而它已经错了。

**三、状态集也只留能产生的。** 文档状态集删掉了 `done`，理由与删掉非 win32 分支一样；写入点只剩 `create` → `planning`、`start` → `in_progress`、`archive` → `completed`。

**四、prompt 层拒绝不了。** `workflow-state` 是每轮注入的、唯一承担「下一步是什么」的通道，因为静态系统提示被观察到漏掉过两个强制步骤。但当 `workflow.md` 里没有当前状态的块时，代码给的不是拒绝，而是一句兜底文本 `Refer to workflow.md for current step.`；压缩之后还有一个回合的窗口。**模型没有返回错误的通道**，这一层唯一的失败形态就是沉默——不是没想到，是层本身的性质。

## 为什么换成这个

**一、拒绝是可归因的，降级不是。** 一次拒绝写明缺什么——「没有可用的 POSIX shell」「计划文件读不出来」「没有已回答的选择题」各指向一个能修的东西；降级只留下一个错误的结果。

**二、代理也会读到拒绝。** 人读到拒绝会去装 Git Bash，代理读到拒绝会转述或改策略；而降级的读者只有人——人不在环里的时候（后台任务、子代理、`unattended: true`），信息就彻底丢了。

**三、降级把「配置错了」变成「数据错了」。** shell 选错、预算没生效都是环境问题，修一次就好；但程序用默认值继续跑，错误会沉淀进产物。**产品里的错误比环境里的错误贵得多**。

## 代价

**一、环境没配好时它什么都不做。** 缺一个 `shellPath`，所有 `myflow_bg_*` 调用都拒绝，直到有人配置——0.3.0 的安装文档必须补上「装 Git for Windows」这条硬前置。

**二、每条拒绝都要自己的一句话，且要和代码同步**——这是三层规格树那笔维护债的同一份账。

**三、「拒绝」是策略，不是保证。** `--allow-unapproved` 与 `--allow-empty-context` 都在命令行上，但都会留痕（前者把 `started_without_approval` 写进 `task.json`）——跳过必须是响亮的、被记录的。

**四、旁证一：状态集删了，读取端没删。** `status.ts` 的 `phaseForStatus` 仍映射 `"done"`，而 `[workflow-state:completed]` 对活着的任务**不可达**：`archive` 先写 `completed`，再移走目录、清掉指针。那个块里的 commit 与 finish-work 两条执行语句由 `workflow-invariant.test.ts` 认证存在——认证通过，被认证的路径基本不运行。

**五、旁证二：载荷边界是一张手维护的清单。** 发布只拷 `.pi/` 和 `.myflow/`，`FORBIDDEN` 挡住 `tests`、`tools`、`.myflow/.runtime`。而新增的顶层目录（比如这本书的 `book/`）既不进载荷、也不在 `FORBIDDEN` 里——它**不发声地没有被拷贝**。[构建、发布、更新、版本](../launch/delivery.md)把这层边界写成了四个互斥模式的现状。

## 什么情况下我会改回去

1. **拒绝挡住的是环境差异，而不是错误。** 判据是「用户什么都没做错」。那时该把检测提前成一次性自检（安装或首次启动时说清缺什么），而不是每次调用都重复拒绝——这是「更早拒绝」，不是降级。
2. **出现真正的 schema 校验器替掉手写正则读配置。** 那时失败会从「读不出来」变成「读出来了但不对」：前者可以降级成警告（用默认值并大声说），后者必须拒绝。
3. **两个 bypass 被用得太频繁。** 那说明默认值错了，该改默认值：所有人都要绕过的门是错误。
4. **prompt 层出现错误通道。** 若 Pi 允许扩展阻止一次 agent 启动并回报理由，缺失的 phase 块就该在那里拒绝。
