# /mysubagents 面板

## 职责

一套"给人看的窗口"，读两套已有的项目注册表：前台的 run（`.myflow/.runtime/subagents/`）和后台任务（`.myflow/.runtime/background/`）。它不拥有任何执行逻辑——每个操作最终都落到控制文件的一行或注册表的一次修改上。这一点决定了一个没派发过任何东西的会话照样能用它。

## 触发点

`/mysubagents` 是真正的 Pi 斜杠命令之一，不经过模型，不消耗 token。

- 参数映射到视图：`board` / `tree` / `background` / `help` / `?`，其它一律进 `menu`。
- 打开时跑一次 `pruneRuns`（不是常驻清理）。
- 有 TUI 时用 `ctx.ui.custom()` 开组件；没有 TUI 时把同样的状态渲染成纯文本报告发进会话。
- 组件自己每 1 000 ms 重建一次状态——和派发方的心跳同节奏。

## 三个视图

| 视图 | 来源 | 能做什么 |
| --- | --- | --- |
| `board` | 前台 run + 后台任务，前台在前 | **只读**：上下移动，`Enter` 打开转录或输出尾部 |
| `tree` | 前台 run，按 `group`（一次派发）分组 | `x` 停这一条、`X` 取消整组、`s` 转向、`r` 重派、`d` 忘掉一条终态、`D` 忘掉所有终态 |
| `background` | 后台任务注册表 | `x` 停、`d` 删一条终态、`D` 删所有终态、`c` prune、`r` 重放同一条命令 |

`?` 打开帮助屏，`/mysubagents help` 打印同一份内容。`q` / `Esc` 返回上一层。

## 读写哪些文件

| 文件 | 职责 |
| --- | --- |
| `board/index.ts` | 命令注册、面板组件、1 秒刷新、光标锚点；唯一 import `@earendil-works/pi-tui` 的地方，且是命令处理器内部的动态 import |
| `board/state.ts` | 把两套注册表读成一个 `BoardState`；`now` 是参数，所以 30 秒的 `stale` 边界可测 |
| `board/render.ts` | 纯排版，不碰终端 |
| `board/keys.ts` | 键 → `Action` 的 reducer，不执行任何副作用 |
| `board/actions.ts` | 执行 `Action`，副作用全部来自注入的实现 |
| `board/transcript.ts` | 把日志 JSONL 变成可读行 |

写入只有两种：`appendControl` 往 `<runId>.ctl.jsonl` 追加一行，或者经 `runs.ts` / `background/` 的 API 改注册表。**从不写内存状态**，所以第二个会话能管理第一个会话派发的 run。

## 不变量

**视图数据只有一份。** 三个视图都从同一个 `BoardState` 渲染，它们不可能对"现在在跑什么"有不同说法。

**光标锚在行身份上，不锚在行号上。** 每秒重建意味着行会移动（一条 run 结束、一次 prune、一组重排）。组件记下选中行的 id（`selectionAnchor`），刷新后再定位回去（`locateAnchor`）；锚定在行号上会让键盘看起来失灵——这个 bug 曾经上线过。

**键盘策略可测，因为没有终端。** `keys.ts` 只返回动作，`actions.ts` 才执行；于是测试可以断言"board 视图永远不会产生 stop"和"tree 的 `x` 停的是这一条"，都不需要起进程。`normalizeKey` 接受注入的 keybindings matcher，用户的键位表决定 `enter` 是什么，测试用字面量兜底；顺带处理了 CSI 与 SS3 两种方向键编码，否则面板会在某一种终端配置里看起来像坏了。

**"只读"是靠没接线，不是靠权限。** `board` 视图的 reducer 里没有接任何管理动作。这是实现选择，不是安全机制。

**动作的拒绝发生在下层。** 对一条还在跑的 run 按 `d`，reducer 照常产出 `delete-run`，由 `deleteRun` 拒绝——因为"这条是不是终态"只有注册表知道。

## 为什么需要它

理由和转向通道是同一条，只是从人的角度说：派发方此刻**卡在自己的工具调用里**，它不能顺便画一个进度条；而你可能是在另一个会话里想知道"刚才那个 check 跑完没有"。这两件事都没有一个"谁来渲染"的答案，除非渲染发生在一个独立、只读盘的地方。

面板还承担一个隐性职责：**让"state 都在盘上"这个设计可被验证**。如果某个状态只活在内存里，面板就会看不到它——一个打不开的面板是最诚实的缺陷报告。

代价是：每秒重建还要让键盘不发抖，就得把 `state` / `render` / `keys` / `actions` 分开，再加一个按大小缓存转录的解析器。

## 一个最小走查

1. 用户输入 `/mysubagents tree`。命令跑一次 `pruneRuns`，读两套注册表，建出分组状态，开组件。
2. 光标落在第一组的第一个 run 上，它 `status: "running"`、心跳 3 秒前。
3. 按 `s`。组件把自己关掉，然后弹一个文本输入框（对话框不压在 1 秒刷新上）。
4. 输入"改成只读 `transport.ts`，别再跑测试"。确认后 `actions.ts` 调 `appendControl`，控制文件多一行。
5. 组件重新打开，光标回到同一行（靠刷新前记下的 `run:r-…` 锚点，不是行号）；一秒后注册表里这条 run 的 `steers[]` 多了一条，面板显示在行下方。

## 常见误解

- **"面板维护一份运行列表。"** 它每次从盘上重建，内存里只有上一次的渲染结果。
- **"只有派发方才停得掉 run。"** 任何会话都行：面板写的是控制文件，派发方会读到。
- **"面板会顺手探一下 pid。"** 不会。`stale` 只由心跳推断，真探 pid 的只有 `x`。
- **"没有 TUI 就用不了。"** 用得了，输出变成一段文本报告；只是键盘操作没有意义了。
